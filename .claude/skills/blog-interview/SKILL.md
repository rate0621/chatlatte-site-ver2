# ブログ執筆インタビュー

ユーザー（chatlatte運営者）へのインタビューを通じてブログ記事を作成し、microCMSに下書き投稿するまでを行う。

## 背景と目的

- ブログ戦略は「実績深掘り」＋「山形ローカル×意思決定キーワード」の2本柱。汎用ハウツー記事は書かない
- 記事の素材はユーザーの実体験にしかない。インタビューでそれを引き出すのがこのスキルの仕事
- サイトのポジショニングは「エンジニアがいない会社の、最初のエンジニア」。読者は非エンジニアの経営者・担当者
- 記事のKPIは問い合わせ（30分無料相談）への貢献

## 進め方（フェーズ制・順番厳守）

### Phase 0: ボイスプロファイルの読み込み

- 最初に必ず `.claude/skills/blog-interview/voice-profile.md` を読む。本人の話し方の癖・価値観・記事化の注意点がまとまっており、インタビューの深掘り方針と記事の文体はこれに従う

### Phase 1: テーマ確定

- 記事のテーマ類型は4つ。引数でテーマが渡されていればそれを使い、なければ候補を提示して選んでもらう：
  1. **実績深掘り**（例：ベンダー未解決のクラウド費問題、サムネイル自動生成、システム引き継ぎ）
  2. **意思決定型**（発注・採用の一歩手前で検索されるテーマ）
  3. **山形ローカル×非IT業種**（治療院・小売等の業務IT化）
  4. **時事・トレンド見解型**：いま市場で話題のトピック（AI・技術・働き方など）に対する本人の見解を聞く。手順と規律：
     - トピック候補はWebSearchで**当日時点の話題**を調査して提示する（古い知識で提案しない）
     - トレンド自体の事実関係（何が起きているか）は検索で裏取りし、記事内では事実と見解を明確に分ける
     - 記事の軸はあくまで**本人の経験に根ざした見解**。ニュースの汎用解説・まとめ記事にしない（見解が乗らないトピックは没にする）
     - 想定読者への意味（エンジニア不在の会社にとってどういう意味を持つか）まで翻訳できるとベスト。ただし毎回無理に問い合わせへ接続しない（人柄・信頼形成が主目的の記事もあってよい）
  5. **蔵書起点・見解型**：自分のKindle蔵書（`/Users/rate/rate/kindle_capture/books/`・別リポ）の一節を「挑発」として使い、本人の見解を引き出す。手順と規律：
     - 選書は `.claude/skills/blog-interview/book-catalog.md`（slug↔邦題↔ジャンル↔フック↔amazon）を見て、**訪問者（非エンジニア経営者）に刺さりそうな2〜3冊を提案**して選んでもらう。**本文（10〜25万字）は主コンテキストに読み込まない**
     - 選書後、**一節の抽出はサブエージェント（Task）に任せる**：`scripts/book-source.sh path <slug>`（`clean <slug>` でも可）のテキストを読ませ、〈短い引用＋なぜ面白いか（訪問者視点）＋投げかける問い＋補強するテーマ類型〉を5〜8個の構造化リストで返させる。主コンテキストにはこのリスト（数KB）だけを持ち込み、本人に提示して**1つの一節**を起点に選んでもらう
     - **記事の軸はあくまで本人の経験に根ざした見解**。本の要約・書評にしない（時事見解型と同じ規律）。一節は「問いを立てるための踏み台」であって主役ではない。本人の実体験・実務に接地しない一節は没にする
     - `scripts/book-source.sh meta <slug>` で書名・amazon URLを控えておく（Phase 4の帰属・アフィリエイトリンクに使う）
     - 蔵書は別リポにあるため、無い環境ではこの類型は使えない（場所は `KINDLE_BOOKS_ROOT` で上書き可）
     - **切り口のバリエーション（どれも同じ機械を使い、フレーミングだけ変える）**：①一節ぶつけ型（時事見解型を補強・一節への逆張り／経験的見解）②実務での反証型（実績深掘り・「本ではこう、でも現場では」）③積読の意思決定型（意思決定型・本のフレームを発注/採用判断に接続）④山形の商売×本の理論型（山形ローカル。※山形は生活拠点で商圏ではない点に注意）⑤複数本の横断テーマ型（1テーマを2〜3冊で見て本人の実践で決着・重め。抽出は本ごとにサブエージェント）⑥自分を作った一冊型（わたしの話/origin系・転機と結ぶ／Phase 6のvoice-profile素材にも）
- テーマ確定時に次の3点を1行ずつユーザーと確認する：**想定読者／読者がこの記事に辿り着く状況（検索語やXの文脈）／記事末尾CTAの文脈**（例：見積もり記事なら「見積もりを見ながら30分話しませんか」）。蔵書起点の場合「辿り着く状況」はたいてい「その本・そのテーマに関心がある経営者」。加えて、その一節が引き出す**本人の実体験の角度**を確認してからインタビューに入る（軸を先に固定する）

### Phase 2: インタビュー（1問ずつ・8〜12問）

- **1メッセージにつき質問は1つだけ**。回答を読んでから次の質問を組み立てる
- 質問の狙い：具体的なエピソード・数字・失敗談・意思決定の分岐点・当時の感情を掘る。読者が追体験できる「シーン」を集める
- 回答が抽象的なら「たとえば？」「そのとき実際は何をしましたか？」で具体化を促す
- 各回答を受け取るたびに `docs/interviews/<slug>.md` に質問と回答を追記して記録する（slugはテーマから英数ケバブケースで決める）
- 記事を書くのに十分な素材が集まったと判断したら「あと◯問で切り上げられますが、他に話しておきたいことはありますか？」と確認して終える

**相槌と質問の型（要約で終わらせない）：**
- 相槌は回答の要約ではなく、**その回答が記事のどこで効くかの命名**にする。悪い例：「なるほど、リスクがあって放置されていたんですね」／良い例：「『消すのはリスクがあるからやりたくない』——**放置の正体は技術ではなく心理の問題**だった、という話ですね。これは記事の核心になります」
- 質問には**回答の粒度指定**を添える：「非エンジニアが読んでも段取りが分かる粒度で」「そのときの言葉に近い形で」など。指定が無いと回答は抽象化する
- 過去の発言・サイト掲載の事実を引用して掘る：「以前◯◯と言っていましたが」「サイトには◯◯と書きましたが」
- **蔵書起点の場合の引用ドリル**：本の一節を引いてから本人の実務に振る。「この本にはこう書かれています——〈引用〉。◯◯さんの現場ではどうですか／賛成ですか反対ですか、実例で」。狙いは**本への相槌ではなく本人のエピソード**。本の話が続いて本人の体験が出てこないときは「その考えを、実際にお客さんとの間で経験した場面はありますか」で必ず現場へ引き戻す（一問一メッセージの規律は変わらない）
- ユーザーが質問で返してきたら（「人手不足ってどういう状況？」等）、こちらが**選択肢やパターンの分解を提示**して答えやすくする。この逆質問はしばしば記事の核心なので歓迎する

### Phase 3: 構成案の承認

以下をまとめて提示し、**承認を得てから**執筆に進む：
- 見出し構成（h2/h3のアウトライン）
- タイトル案3つ（検索意図とXでのクリックを意識した差のある3案）
- **description案**（100〜120字。検索結果でのクリックを意識し、記事の中身に忠実に）
- 付けるタグ（1〜2個。`post-draft.sh tags` で実在タグ一覧を取得して提示。1記事が複数のタグにまたがってよい——例：実績の話でも読者への教訓が強ければ「考えごと」も付ける）

※ microCMSスキーマは title / content / description / tags（複数）/ eyecatch。タグ一覧（2026-07-07時点）：やってきたこと・AIとの付き合い方・わたしの話・考えごと・東北のくらし。旧categoryフィールドは残っているが未使用（参照しない）

### Phase 4: 執筆

**執筆前の必須手順（順番通りに）：**
1. **お手本を1本読む**：`docs/interviews/` にある既存の完成記事HTML（例：`ai-labor-shortage.html`）を1本読み、分量・見出しの付け方・導入の型・トーンを合わせる
2. **ファクトリストを作る**：インタビュー記録から「記事で使う事実・数値・エピソード・本人の言い回し」を抜き書きする。**数字付きのエピソードは原則すべて使う**（取りこぼしが最頻の品質劣化）。使わないと決めた素材は理由を持って除外する
3. 構成案（Phase 3で承認済み）に沿って執筆する

- 出力先：`docs/interviews/<slug>.html`
- **分量の目安：2,500〜3,500字**。主要な論点は箇条書きに圧縮せず、h3見出しで1つずつ段落を割いて論じる（箇条書きは手順・列挙などの補助に限る）
- **形式**：microCMSリッチエディタ互換のプレーンHTML。使用タグは `h2 / h3 / p / ul / ol / li / blockquote / strong / a` のみ。class属性・style属性・スクリプトは使わない。**blockquoteは実際の発言・会話の引用専用**（自分の主張の装飾に使わない）
- **本の引用（蔵書起点の場合の著作権ルール）**：①**短い引用のみ**（1〜2文。章要約で本文を代替しない。主＝本人の主張／従＝引用の関係を保つ——著作権の引用要件）②**書名・著者を同じ段落で明示**（例：「『エッセンシャル思考』（グレッグ・マキューン）にこうあります」）③**本の引用に `blockquote` は使わない**（blockquoteは本人の発言専用）。本の一節は帰属を含む `<p>` の中で「」括りにする
- **書籍カード（蔵書起点は必ず入れる）＝マーカー方式**：記事本文にHTMLでカードを組まない（microCMSが `<img>` を正規化し `<div>`/style を落とすため、枠線・横並びのカードは本文HTMLでは作れない）。代わりに**サイトの `<BookCard>` コンポーネント**（`src/app/components/BookCard.tsx`）を使い、本文にはマーカーだけ置く。手順：
  1. `book-source.sh meta <slug>` で amazon URL・cover パスを取得し、`post-draft.sh upload <coverパス>` で書影をmicroCMSにアップしてURLを得る
  2. amazon URL（`amzn.to/...`）をリダイレクト追跡してASINを解決：`curl -s -o /dev/null -w '%{url_effective}' -L "<amzn.to URL>"` の結果から `/dp/<ASIN>` を抜く（`book-source.sh meta` の amazon を使う）
  3. `src/lib/book-fallbacks.ts` の `BOOK_FALLBACKS` に1エントリ追記：`"<ASIN>": { title, author, publisher?, imageUrl:<アップした書影URL>, url:<amzn.to URL> }`
  4. **その本を初めて紹介・引用した段落（`<p>`）の直後**に **`<p>[[bookcard:<ASIN>]]</p>`** を入れる（末尾ではなく、本を出したすぐ下にカードを出す）。その段落に書名のインラインリンクは付けない（直下のカードと重複するため）
  - サイトが `[[bookcard:ASIN]]` を検出し、`BOOK_FALLBACKS` の自前データでカードを描画。**Creators API（`src/lib/creators-api.ts`）の審査が通れば発売日・売上ランキングを自動で追加**（`.env` の `AMAZON_PAAPI_ACCESS_KEY/SECRET_KEY/PARTNER_TAG`。現状アカウントは `AssociateNotEligible` で発売日/ランキングは非表示、自前データでカード自体は出る）
- **開示文は書かない**：サイトは本文にAmazon/楽天/A8リンクまたは `[[bookcard:` を検出すると記事冒頭に `[PR] …` バナーを自動表示する（`page.tsx` の `hasAffiliateLink`）。**手動の開示文は入れない**（2026-07-14）
- 本文に画像を直接置く場合の注意：microCMSは保存時に `<img>` を正規化し `?w=` クエリ削除・width/heightを実寸化する。表示サイズはサイトCSS（`prose-img:max-h-72 …`）で決まる
- 反映には**再デプロイが必要**（ISRなし。公開済み記事も初回レンダリングでキャッシュされるため、内容・コード変更はデプロイまで本番に出ない）
- **事実厳守（最重要）**：インタビュー回答にない事実・数値・固有名詞を書かない。誇張しない。文章の都合で事実が欲しくなったら創作せずユーザーに確認する。顧客名・サービス名（Vercel等）は出さない方針を踏襲
- **事実は文脈ごと使う（ドリフト禁止）**：時制・主語・言い回しを保つ。悪い例——記録「ある現場で月150時間削減を実現した」→ 記事「私はふだん月150時間分をAIに任せています」（時制と性質が変わり別の主張になる）。記録「経験の記述が無い」のに「〜という相談をいただくことがあります」と書くのは**経験の創作**であり最も悪質。迷ったら記録の文言に近づける
- 文体：です・ます調。専門用語は使わない（使う場合は一文で平易に言い換える）。サイトと同じ「ちょっと聞いていい？」の温度感
- 一人称は「私」。読者への呼びかけは「〜ではないでしょうか」程度に控えめに
- **自分の手柄を説明的に強調しない**（本人フィードバック済み）：「提案したのは私のほうです。つまり〜」のような念押しはNG。「軽く提案してみました」程度の自然な言及にとどめる
- 関係者は協働の距離感で書く：「相手は」ではなく「ご一緒していた」。断定の連打より「〜かなと思っています」「〜かもしれません」の柔らかさを混ぜる
- **記事末尾のCTAは毎回入れない**（本人フィードバック 2026-07-10：「毎回CTAに誘導するのは俺らしくない」）。押し売りは本人らしくないので、デフォルトは無料相談リンクを付けない。読者が自分で動ける締め——問いかけ（「一度整理してみてはいかがでしょうか」）や、行動しないと損する軽い警句（「じゃないと、せっかくのツールがただの置物になってしまうかもしれません」）——で終える形を基本にする
- CTAリンク（`https://www.chatlatte.com/#contact`）を入れるのは、Phase 1でCTA文脈を強めに確定した記事だけに絞る（例：見積もりを見ながら相談、など明確な導線がある回）。入れる場合も1段落・押し売りしないトーン。それ以外は上記の「自分で動ける締め」にする

### Phase 5: microCMSへ下書き投稿

```bash
.claude/skills/blog-interview/scripts/post-draft.sh post docs/interviews/<slug>.html \
  --title "タイトル" --description "説明文" --tag "タグID" [--tag "タグID2" ...]
```

- 成功したら返却されたコンテンツIDと管理画面URLを提示する
- **改稿時**：既存下書きは `PATCH ${BASE}/blogs/<コンテンツID>` で上書き更新する（APIキーにPATCH権限あり・疎通確認済み）。新規下書きを乱立させない
- 401/403で失敗した場合：`.env` に `MICROCMS_WRITE_API_KEY`（POST権限付きAPIキー）を設定してもらう（2026-07時点では既存の `MICROCMS_API_KEY` にPOST権限があり、そのまま動作確認済み）

### Phase 5.5: X版の生成

下書き投稿が済んだら、記事のX（Twitter）用再編集版を `docs/interviews/<slug>-x.md` に出力する。**全文転載は禁止**（サイトへの訪問理由が消える＋SEOでX側が勝ってしまうため）。

- **本文ポスト**：800〜1200字のネイティブ長文。記事の一番おいしいエピソードと洞察を全体の6〜7割まで出し切る（ケチると読まれず、全部出すとサイトに来ない）。1行目はタイムラインで単独表示される前提のフックにする。**本文にリンクは入れない**（リーチ減衰対策）。ハッシュタグは使わない。ボイスプロファイルの語り口を適用
- **リプ用ポスト**：ツリーの2件目として投稿する短文＋記事URL（`https://www.chatlatte.com/blog/<コンテンツID>`）
- 長文ポストが使えない場合に備え、3〜5分割のツリー版も needed なら提示できる旨をユーザーに伝える
- **投稿タイミングの注意**：記事の公開＋Vercel再デプロイが済んでからXに投稿する（先に投稿するとリンク切れ・OGP不発になる）

### Phase 5.6: アイキャッチ生成

`scripts/make-eyecatch.sh` でアイキャッチ画像（1200×630、記事OGP兼用）を生成する。

```bash
.claude/skills/blog-interview/scripts/make-eyecatch.sh docs/interviews/<slug>-eyecatch.png \
  "タイトル（**強調部分**をマーカーで指定）" --tag "タグ名1" [--tag "タグ名2" ...] [--dark]
```

- `--tag` にはPhase 5で `post-draft.sh post` に渡したのと同じタグ名（IDではなく表示名）を渡す。右上に横並びのピルで表示される。複数タグでも自動で並ぶ
- タイトルの「——」以降は自動でサブタイトルに分離される。強調マーカーは数字・断言・固有ワードに使う（1〜2箇所まで）
- テーマの使い分け：**ミルク（標準）**が基本。事件性・強い断言の記事は `--dark`（エスプレッソ）でリズムを出す
- 生成したPNGは `post-draft.sh eyecatch <コンテンツID> <PNG>` で自動設定する（メディアアップロード→eyecatchへPATCH。2026-07-06疎通確認済み）
- **`make-eyecatch.sh` に渡した実際のタイトル文字列（強調マーカー・「——」込み。記事のtitleフィールドとは別物になりうる）を、必ず `docs/interviews/eyecatch-manifest.md` に追記する。** タグ変更などで将来再生成するときは、画像から逆算せずこの記録の文字列をそのまま使う（逆算すると強調位置や「——」の有無がズレてレイアウトが崩れる。2026-07-07に実際に発生）
- eyecatchを設定すると記事ページのOGP画像・Twitterカード（summary_large_image）としても使われる

### Phase 6: ボイスプロファイルの更新と完了案内

**ボイスプロファイル更新**：インタビュー全体を振り返り、「この人の人格・価値観・話し方を表している」と思える発見（新しい信念、口癖、仕事観、関わり方のパターンなど）があれば候補として提示し、**本人の確認を得てから** `voice-profile.md` に日付・出典つきで追記する。既存項目と重複するものは追記しない。

完了案内として以下を必ず伝えて終える：
1. アイキャッチ画像は管理画面で手動設定が必要（自動化は将来対応）
2. 下書きを確認して公開ボタンを押すのはユーザー自身
3. **公開後、Vercelの再デプロイをしないとサイトに反映されない**（ISR未設定のため）

## してはいけないこと

- 下書きを飛ばして公開状態で投稿すること
- インタビューを省略して記事をでっち上げること（過去回答の使い回しは、ユーザーが明示的に許可した場合のみ）
- 1メッセージに複数の質問を詰め込むこと
